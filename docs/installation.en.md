# Installation, updates and releases

[中文](installation.md)

## Manage Windows with Scoop

After the first Release and bucket manifest are published:

```powershell
scoop bucket add dev-tools https://github.com/hhhxxxddd/dev-tools
scoop install dev-tools/dev-tools
dev-tools help
scoop update dev-tools
scoop uninstall dev-tools
```

The manifest installs `main/pwsh`, `main/mise` and the Python 3.14.8 controller host, and creates a `dev-tools` shim. No Git clone or profile function is required. The marked dev-tools blocks from older installers are removed; open a new terminal to discard an already loaded function.

Stop active Windows projects before updating or uninstalling, for example `dev-tools -e win stop my-app`. Hooks verify PID and start time and reject removal of files used by active workers. Preferences, registrations, state, caches and project runtimes remain. Scoop operations do not update or uninstall WSL.

## Deploy and update WSL

After installing with Scoop, deploy once from Windows and update explicitly afterwards:

```powershell
dev-tools self install -e wsl
dev-tools self status --json
dev-tools self update -e wsl
```

Both deployment commands share the flow and can be repeated. They deploy the same local package version into `[wsl].distro`, without entering Linux to clone a repository. Stop projects in that distro first, for example `dev-tools -e wsl stop my-app`, then `start` as needed after deployment. The installer rejects overwriting files used by active workers, preserves registrations, preferences, state, caches and project runtimes, and never prepares or starts projects automatically.

The distro must already exist with systemd enabled. Missing mise/rsync use extrepo/APT on Debian/Ubuntu; install them yourself on other distributions. The program lives in `/opt/dev-tools`, its controller host in `/opt/dev-tools/host-mise`, and its entrypoint in `/usr/local/bin/dev-tools`. Windows executable directories and caches are not shared.

`dev-tools`, `dev-tools help` and top-level `--help` share the overview. A read-only file probe with a five-second timeout checks WSL source, entrypoint and host. Missing or incomplete deployment shows deployment instructions; unavailable WSL, invalid distro or timeout shows a distro diagnostic. Help never installs, upgrades or executes the WSL controller. Individual command help skips the probe.

Native WSL can update from the latest stable Release, verifying that Release's SHA256SUMS and per-file package inventory before deployment:

```bash
sudo dev-tools self update -e wsl
sudo dev-tools self update -e wsl --source /path/to/dev-tools
```

Before the first Release exists, deploy from Windows or supply `--source`. The source must be a checkout with the official origin or a package generated by the release flow. Windows `self install/update -e win` directs you to Scoop. `self status --json` uses stable fields and never synchronizes versions automatically.

## Source installations

`scripts/bootstrap.ps1` still deploys both platforms, `scripts/install.ps1` installs the Windows profile entrypoint, and `sudo bash scripts/install.sh` deploys WSL. Bootstrap and the Windows WSL helper verify Git origin before running installers. Run `git pull --ff-only`, then rerun the installer or `self update -e wsl` to update deployment.

## Release maintenance

The controller version must match `pyproject.toml` and the tag. Complete both platform test suites and Ruff, then build a candidate:

```powershell
$env:PYTHONPATH = "$PWD\src"
python -m dev_tools.release --tag v0.4.0 --output dist
```

Outputs are `dev-tools-<version>.zip`, `SHA256SUMS` and `dev-tools.json`. The ZIP includes both platform programs, documentation, examples and a per-file SHA256 inventory. Ordering, timestamps and line endings are fixed; uncompressed entries avoid differences between platform compression libraries. Caches and `*.local.*` are excluded. The Scoop manifest uses the actual ZIP SHA256.

You can first create a GitHub Release draft targeting committed source, upload all three assets, and use `docs/releases/v<version>.md` for the notes. Drafts do not trigger the release workflow.

Pushing a matching `v<version>` tag or publishing a GitHub Release runs `.github/workflows/release.yml`, which verifies both platforms and builds the assets. An existing draft gets updated assets and is published; an existing public Release is checked against the build without overwriting its assets. The workflow then updates `bucket/dev-tools.json` on the default branch. Manual runs from a regular branch only verify and build; they do not publish. Repository write permission is required; if branch protection blocks direct writes, merge the Release manifest through a PR.

Publishing the first Release and bucket manifest is a separate maintenance action. Local code and `dist` candidates alone do not make public `scoop install dev-tools/dev-tools` available.

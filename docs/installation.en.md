# Installation, updates and releases

[中文](installation.md)

## Manage Windows with Scoop

The Scoop manifest is maintained in [hxd-box](https://github.com/hhhxxxddd/hxd-box) and follows official releases. Git installation uses the current source.

```powershell
scoop bucket add hxd-box https://github.com/hhhxxxddd/hxd-box
scoop install hxd-box/dev-tools
dev-tools help
scoop update dev-tools
scoop uninstall dev-tools
```

The manifest installs `main/git`, `main/pwsh`, `main/mise` and the Python 3.14.8 controller host, and creates a `dev-tools` shim. No Git clone or profile function is required. The marked dev-tools blocks from older installers are removed; open a new terminal to discard an already loaded function.

`dev-tools upgrade` lists active Windows projects and accepts `Y` (or `--yes`) to stop, update and restore their previously active services. Direct Scoop updates and uninstall still require stopping projects first, for example `dev-tools -e win stop my-app`. Hooks verify PID and start time and reject removal of files used by active workers. Preferences, registrations, state, caches and project runtimes remain. Scoop operations do not update or uninstall WSL.

## Deploy and update WSL

After installing with Scoop, deploy once from Windows and update explicitly afterwards:

```powershell
dev-tools self update -e wsl
dev-tools self status -e wsl --json
```

`self update` handles both first installation and updates and can be repeated. They deploy the same local package version into `[wsl].distro`, without entering Linux to clone a repository. When projects are active, enter `Y` to record and stop services and monitors, deploy, and restore only what was previously running through the new entrypoint. Previously stopped projects stay stopped. Use `--yes` for unattended operation. The installer still rejects active workers and preserves registrations, preferences, state, caches and project runtimes. First installation does not register or start projects.

The distro must already exist with systemd enabled. Debian/Ubuntu use extrepo/APT for missing rsync, or for missing mise when a first deployment has no external Python binding; install them yourself on other distributions. The program lives in `/opt/dev-tools`, with its entrypoint in `/usr/local/bin/dev-tools`. A first installation without an external interpreter prepares Python in `/opt/dev-tools/host-mise`; subsequent deployments preserve the `.host-python` binding. Windows executable directories and caches are not shared.

`dev-tools`, `help` and command help report missing deployments or differing versions. Explicit `-e wsl` / `-e win` help and `-v` query the actual target. These queries never install, update or start projects. Unsupported cross-platform commands or execution contracts are blocked before execution; stopping and controller updates remain available.
Each side maintains its own installation. After updating Windows, run `dev-tools self update -e wsl` from Windows to deploy the current code to WSL; redeployment also works when versions match. `list` queries only the current environment by default; `list --all` queries both. An unavailable side produces a yellow notice while retaining the other side's results, and does not imply that an update is required. `dev-tools list -e wsl` queries WSL alone.

Native WSL can fetch a new version or redeploy its recorded source:

```bash
sudo dev-tools upgrade -e wsl
sudo dev-tools self update -e wsl --source /path/to/dev-tools
```

`self update` does not fetch a new version. If native WSL has no recorded source directory, supply the current checkout or release package through `--source`. You can also deploy the package installed on Windows. The source must be a checkout with the official origin or a package generated by the release flow. `self update -e win` reruns the Windows installer from a verified source without fetching a new version. Scoop installations redeploy only their current package, do not modify the profile, and reject a different `--source`. Scoop upgrade rejects --source to keep its shim on the selected installed version. `self status --json` describes only the selected target; use `-e win/wsl` to inspect the other side. It never synchronizes versions automatically.

### Upgrade the controller directly

`dev-tools -v` / `--version` only print the controller version. `dev-tools upgrade` fetches and deploys new code on the current platform; `-e win` / `-e wsl` selects the target from either side. `dev-tools self upgrade` is another entrypoint for the same operation and accepts the same `-e` and `--source` options. Scoop installations on Windows use Scoop. Source installations verify Git origin, reject local changes, detached branches, tracking outside origin and divergent histories, and only fast-forward. Confirm with `Y` or `--yes` to stop and restore active projects. Updating shared Windows controller source also handles Windows projects using that source. Failed WSL deployment restores a controller backup. Failed restoration keeps a native recovery record; retry with `dev-tools self recover -e wsl` (use `sudo` in native WSL) or `dev-tools self recover -e win`. Projects explicitly stopped by the user during the update are skipped during restoration.

Native WSL `upgrade` prefers the checkout recorded in `.source`; if no Git checkout is available, it downloads the latest stable Release and verifies SHA256SUMS and the per-file package inventory before deployment. Explicit `--source` for upgrades requires a verified Git checkout. Source installations can run `dev-tools upgrade -e win` without manually pulling first, or select a source with `dev-tools upgrade --source <checkout>`. `self update` redeploys current code without fetching source or downloading a Release; supply `--source` if the recorded source is unavailable.

From WSL, use `dev-tools upgrade -e win` to upgrade Windows, or `dev-tools self update -e win` / `dev-tools self recover -e win` to redeploy or recover it. Linux sudo is unnecessary; Windows administrator requirements follow the target operation. On both sides, `self update` redeploys current code and `upgrade` fetches a newer version.

## Source installations

`scripts/bootstrap.ps1` still deploys both platforms, `scripts/install.ps1` installs the Windows profile entrypoint, and `sudo bash scripts/install.sh` deploys WSL. Bootstrap and the Windows WSL helper verify Git origin before running installers. Run `git pull --ff-only`, then rerun the installer or `self update -e wsl` to update deployment.

### Use external Python

Source installations select Python from `DEV_TOOLS_PYTHON`, an existing native binding, then the default mise host. Windows uses `.host-python.win` and WSL uses `.host-python`; shared checkouts do not consume the other platform's binding. The interpreter must be native to the target platform, support `>=3.14.8,<3.15`, and provide the SSL and TOML standard libraries. An invalid explicit path or existing binding fails installation instead of falling back to another Python. The installer records the real absolute executable path; changing a `current` link does not automatically switch the binding.

Use an existing native interpreter on Windows:

```powershell
$env:DEV_TOOLS_PYTHON = (Get-Command python).Source
.\scripts\install.ps1
Remove-Item Env:DEV_TOOLS_PYTHON
```

Use an administrator-provided shared interpreter in WSL:

```bash
sudo env DEV_TOOLS_PYTHON=/opt/dev-runtimes/python/3.14.8/bin/python3 bash scripts/install.sh
```

When deploying from Windows, `scripts/install-wsl.ps1 -Python /opt/dev-runtimes/python/3.14.8/bin/python3` selects a path in the target WSL distro; Windows interpreter bindings are not passed into WSL.

External mode never installs or upgrades Python and does not require mise to start the controller; projects using mise still need it. The administrator maintains external Python, which dev-tools updates and removal never delete. Projects can reference the same base installation with `mise link python@3.14.8 /opt/dev-runtimes/python/3.14.8`; root mise files still declare versions and each project keeps its dependencies in its own `.venv`. The base installation should be root-owned and readable/executable by all consumers. Keep project dependencies out of the shared base installation.

## Release maintenance

Versions in the controller, pyproject and tag must agree. Build and verify a local candidate:

```powershell
$env:PYTHONPATH = "$PWD\src"
python -m dev_tools.validation
python -m dev_tools.release --output dist
python -m dev_tools.package_smoke dist/dev-tools-0.5.6.zip
```

Outputs are `dev-tools-<version>.zip`, `SHA256SUMS` and `dev-tools.json`. The complete ZIP contains both entrypoints, configuration, examples and documentation; machine bindings, caches and local overrides are excluded. File hashes, version and source commit/dirty provenance are recorded in `.release.json`. SHA256 detects changed bytes; authenticity depends on obtaining the archive and checksums from the official GitHub release or Scoop channel.

Tagging committed clean sources with `v<version>` starts `.github/workflows/release.yml`. It reuses Windows/Ubuntu CI, requires official builds to match the tag, verifies extracted entrypoints, and compares the two native asset sets byte for byte. Release notes must exist at `docs/releases/v<version>.md`. Only the publication job has repository write permissions.

An existing draft can receive the validated assets and then be published. An existing published release is checked against rebuilt assets and is never overwritten. Manual runs on an ordinary branch validate candidates without publishing. Each official release generates a `dev-tools.json` asset for hxd-box to synchronize and maintain its bucket manifest. This repository's release workflow does not automatically push bucket updates.

Source deployments use a verified Git origin. Package deployments verify the complete receipt before running installers. Deployment preserves external Python, registrations, preferences and state. Real WSL lifecycle and bidirectional transport checks remain required before tagging; Ubuntu CI alone does not cover Windows↔WSL behavior.
